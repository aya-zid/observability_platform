## What This Is

Medianet Observability is a multi-tenant SaaS platform that provides:

- **Host and container discovery** — agents auto-detect running services
- **Real-time dashboards** — CPU, memory, disk, network, per-service metrics
- **Log aggregation** — centralized log collection and search
- **Smart alerting** — 60+ alert templates with cross-tier correlation
- **AI-powered reports** — daily summaries generated by Gemini/Groq
- **CVE vulnerability scanning** — automatic NVD correlation against service versions
- **Multi-tenant billing** — subscription plans with usage limits

Customers sign up, install a lightweight agent on their servers, and the platform handles the rest.

## Backend Internals — What Runs in the Background

The Go backend is not just an API server. It runs **6 background workers** that continuously process data, evaluate rules, and maintain system health. These workers start automatically when the backend boots and run as goroutines for the lifetime of the process.

### Background Workers

| Worker | Interval | What It Does |
|---|---|---|
| **Alert Engine** | Configurable (default: every 30s) | Evaluates all enabled alert rules against live telemetry |
| **Notification Dispatcher** | Continuous (event-driven) | Sends email notifications when alerts fire or resolve |
| **Usage Metering** | Every 5 minutes | Flushes Redis usage counters to PostgreSQL daily rows |
| **Subscription Expiration** | Every 1 hour | Checks for expired subscriptions and 14-day trials |
| **Retention Cleanup** | Every 1 minute | Enforces per-plan log/metric retention in Loki and VictoriaMetrics |
| **CVE Scanner** | Configurable (default: every 2 hours) | Scans NVD for CVEs matching discovered service versions |

### 1. Alert Engine

The alert engine is the most complex background worker. Here is exactly how it works:

**Startup:**
- Reads all enabled alert rules from the database
- Starts a ticker that fires on a configurable interval (default: every 30 seconds)

**Evaluation cycle (every tick):**

1. **Load rules** — fetches all enabled `AlertRule` records from PostgreSQL, along with their scopes and thresholds

2. **For each rule:**
   a. **Resolve scopes** — determines which hosts, services, or virtual hosts this rule applies to
   b. **Build query** — maps the template ID to a PromQL or LogQL query. For example:
      - `host_cpu` template → `100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)` with tenant/host label filters
      - `nginx_5xx` template → `rate(nginx_http_requests_total{status=~"5.."}[5m]) / rate(nginx_http_requests_total[5m]) * 100` with domain filter
      - `postgres_connections` template → `pg_stat_activity_count` with tenant/service filters
   c. **Query VictoriaMetrics or Loki** — sends the PromQL/LogQL instant query
   d. **Evaluate thresholds** — compares the returned value against each threshold using the configured operator (`>`, `<`, `==`, `>=`, `<=`)
   e. **Check duration** — the condition must be true for the configured `for_duration` (default: 5 minutes). The engine tracks when a condition first became true and only fires after the duration elapses

3. **Handle breaches:**
   - If the condition is true and no existing firing event exists for this threshold+host combination → creates a new `AlertEvent` record with status `firing`
   - If a firing event already exists → updates the `actual_value` and `last_seen_at`
   - Sends email notification to configured channels
   - Logs the breach to the backend console

4. **Handle resolutions:**
   - If the condition is false and a firing event exists → marks it as `resolved` with `resolved_at` timestamp
   - Sends resolution notification email

5. **Deduplication:**
   - Each event has a dedup key based on rule ID + host + service + threshold
   - Prevents duplicate alerts within a cooldown period
   - If an event is already firing for the same combination, it updates rather than creates a new one

**Supported template categories (60+ templates):**

| Category | Templates | Metrics Source |
|---|---|---|
| Host | CPU, memory, disk, swap, load, disk I/O, conntrack, network errors, SSH brute force, OOM, service crashes | VictoriaMetrics (node_exporter) |
| Nginx | Connection saturation, traffic drops, brute force, 5xx rate, 4xx rate, P99 latency, worker saturation | VictoriaMetrics (nginx metrics) |
| Apache | Connections, traffic, brute force, error rates, latency, workers | VictoriaMetrics (apache metrics) |
| PostgreSQL | Connections, deadlocks, cache hit rate, replication lag, long transactions, temp files, auth failures | VictoriaMetrics (postgres_exporter) |
| MariaDB | Connections, deadlocks, cache hit rate, replication lag, long transactions, temp files, auth failures | VictoriaMetrics (mysqld_exporter) |
| Redis | Memory, evictions, cache hit rate, blocked clients, rejected connections | VictoriaMetrics (redis_exporter) |
| PHP-FPM | Worker saturation, queue depth, slow requests, max children, OPcache | VictoriaMetrics (php-fpm_exporter) |
| Container | Stopped, CPU, memory | VictoriaMetrics (container metrics) |
| Host service | Service stopped | VictoriaMetrics (systemd metrics) |

### 2. Notification Dispatcher

Runs as a background goroutine that processes a notification queue.

- When the alert engine detects a breach or resolution, it writes a notification event
- The dispatcher picks it up and sends HTML emails to all configured notification channels
- Emails include: alert name, severity, service type, hostname, current value vs threshold, dashboard link
- Uses the SMTP configuration from `.env`
- If SMTP is not configured, notifications are logged to the console only
- Failed email sends are retried with exponential backoff

**Email templates include:**
- Alert fired (with severity color coding)
- Alert resolved
- Team invitation
- Password reset
- SMTP test verification

### 3. Usage Metering

Tracks resource consumption per tenant for billing and plan enforcement.

**How it works:**

1. Every 5 minutes, the metering worker:
   a. Reads Redis counters: `usage:{tenant_id}:{date}:log_bytes` and `usage:{tenant_id}:{date}:metric_samples`
   b. Upserts a `TenantUsageDaily` row in PostgreSQL, incrementing `log_bytes_ingested` and `metric_samples_ingested`
   c. Resets the Redis counters

2. The backend increments Redis counters on every ingest:
   - Each log batch → adds byte count to Redis counter
   - Each metrics batch → adds sample count to Redis counter

3. The `TenantUsageDaily` table is used to:
   - Enforce daily log byte quotas per plan
   - Show usage on the billing page
   - Generate usage reports for the admin panel

### 4. Subscription Expiration Checker

Runs every hour to maintain subscription lifecycle:

1. **Expired subscriptions** — finds subscriptions where `current_period_end` is in the past → marks them as `expired`
2. **Trial expiration** — finds Trial plan subscriptions older than 14 days → marks them as `expired`
3. **Grace period** — allows a buffer period before suspending access
4. When a subscription expires:
   - The tenant's `subscription_status` is updated
   - Agent ingest continues working (data is not lost)
   - Dashboard access shows the "Subscription expired" page
   - The tenant can reactivate by selecting a new plan

### 5. Retention Cleanup

Runs every 1 minute to enforce per-plan data retention policies.

**How it works:**

1. For each tenant with an active subscription:
   a. Reads the plan's `log_retention_days` and `metrics_retention_days`
   b. Calculates the cutoff date (today minus retention days)
   c. Deletes old log data from Loki using LogQL delete commands
   d. Deletes old metric data from VictoriaMetrics using delete API

2. This ensures:
   - Free plan: 3 days logs, 7 days metrics
   - Basic plan: 7 days logs, 14 days metrics
   - Pro plan: 14 days logs, 30 days metrics
   - Premium/Enterprise: 30 days logs, 60-90 days metrics

3. Without this worker, data would accumulate indefinitely and consume storage.

### 6. CVE Vulnerability Scanner

Scans discovered services against the NIST NVD database.

**How it works:**

1. Runs on a configurable interval (default: every 2 hours)
2. For each discovered service with a known version:
   a. Maps the service name to an NVD product using the catalog (e.g., `nginx` → `nginx/nginx`, `postgresql` → `postgresql/postgresql`)
   b. Queries the NVD API: `GET https://services.nvd.nist.gov/rest/json/cves/2.0?keywordSearch={product}:{version}`
   c. Parses the response to extract CVE IDs, CVSS scores, severity, descriptions
   d. Matches CVEs against the service version using CPE version ranges
   e. Filters by minimum severity (configurable: MEDIUM/HIGH/CRITICAL)
3. Results are stored in the `service_vulnerabilities` table
4. New high-risk CVEs appear in the Vulnerabilities tab on the Alerts page
5. Each service tracks its scan status: `not_scanned` → `scanned` / `failed` / `unsupported`

**Rate limiting:**
- Without API key: ~5 requests per 30 seconds
- With API key: ~50 requests per 30 seconds
- The scanner respects rate limits and backs off when needed

### Data Flow Summary

```
Agent (host)
    |
    |-- POST /ingest/hosts/register     --> Backend --> PostgreSQL (hosts table)
    |-- POST /ingest/hosts/heartbeat    --> Backend --> PostgreSQL (update last_seen_at)
    |-- POST /ingest/discovery/*        --> Backend --> PostgreSQL (discovered_services, containers)
    |-- POST /ingest/metrics            --> Backend --> VictoriaMetrics (via vminsert proxy)
    |-- POST /ingest/logs/*             --> Backend --> Loki (via LogsProxy, tenant isolation)
    |-- POST /ingest/traces/*           --> Backend --> Tempo (via TracesProxy, tenant isolation)
    |
    v
Backend background workers:
    Alert Engine     -- reads rules, queries VM/Loki, creates events, fires notifications
    CVE Scanner      -- queries NVD API, stores vulnerabilities
    Usage Metering   -- Redis counters --> PostgreSQL daily rows
    Subscription     -- checks expiration, updates status
    Retention        -- deletes old data from Loki/VM per plan limits
    Notification     -- sends emails via SMTP
```

### Multi-Tenant Isolation

Every data path enforces tenant isolation:

- **Metrics:** VictoriaMetrics URL path includes tenant ID: `/insert/{tenantID}/prometheus/api/v1/write`
- **Logs:** Loki `X-Scope-OrgID` header is set to the tenant's UUID
- **Traces:** Tempo `X-Scope-OrgID` header is set to the tenant's UUID
- **Database:** Nearly every table has a `tenant_id` column with an index
- **API:** All platform API routes are scoped to the authenticated tenant
- **Agent auth:** API key is resolved to a tenant via Redis cache or PostgreSQL fallback

No tenant can ever see another tenant's data.

## Containers and Services

### Starting the Platform

```bash
# 1. Create the shared network (one-time)
docker network create obs-network

# 2. Start the observability stack (VictoriaMetrics, Loki, etc.)
cd ../infrastructure
docker compose up -d

# 3. Start the platform
cd ../platform
docker compose up -d --build
```

### What Each Container Does

**obs-backend** (Go API)
- The central brain. Handles auth, data ingestion, query proxying, alerts, billing, reports.
- Reads `.env` for all configuration.
- Mounts `../agent` read-only for install scripts.

**obs-frontend** (React)
- Customer-facing dashboard UI. Runs Vite dev server in development.
- In production, built as static files and served by nginx.

**obs-admin-frontend** (React)
- Platform admin panel for managing tenants, subscriptions, and packs.
- In production, nginx also proxies `/api/` to the backend.

**obs-postgres** (PostgreSQL 16)
- Primary database. Stores all tenant data, users, services, alerts, reports.
- Data persists in `postgres-data` Docker volume.
- Exposed on host port 5434 for external tools (pgAdmin, DBeaver).

**obs-redis** (Redis 7)
- Used for: session storage, rate limiting, API key caching, usage counters, report dedup.
- Ephemeral by default (no persistence). Set a password for production.

**obs-pgadmin** (pgAdmin 4)
- Web UI for browsing the PostgreSQL database.
- **Dev only — remove for production.**

## Customer Platform Guide

### Signup and Login

**Signup** (`/signup`):
- Company name, full name, work email, phone (optional), password
- Password requirements: 8+ chars, uppercase + lowercase + number
- On signup: a tenant is created, a subscription is assigned (Trial by default), and you are logged in

**Login** (`/login`):
- Email + password

- If your account is deactivated, you see an "Account deactivated" page

**Forgot Password** (`/forgot-password`):
- Enter your email, receive a reset link (expires in 1 hour)
- Click link, set new password

### First Steps After Login

After logging in, you land on the **Overview** page. The typical workflow:

1. **Go to Settings** → get your API key and install command
2. **Install the agent** on your server
3. **Wait for discovery** — the agent auto-detects running services
4. **Go to Services** → configure each detected service (log paths, metrics endpoints)
5. **Install integration scripts** to start collecting logs and metrics
6. **Set up alert rules** to get notified of issues
7. **Check the Overview** dashboard to see your infrastructure

### Installing the Agent

The agent is a lightweight OpenTelemetry Collector binary that runs on your server. It collects metrics, logs, and heartbeats, and sends them to the platform.

**Step 1: Get your install command**

Go to **Settings** → **API Keys** page. You will see a pre-generated install command like:

```bash
curl -fsSL 'http://your-platform:8080/install.sh?api_key=YOUR_KEY&machine_id=$(cat /etc/machine-id)' | sudo bash
```

**Step 2: Run it on your server**

SSH into your server and paste the command. The agent will:
1. Download and install the OpenTelemetry Collector
2. Configure it with your API key and platform endpoint
3. Register the host with the platform
4. Start collecting metrics (CPU, memory, disk, network) every 15 seconds
5. Send heartbeats every 30 seconds
6. Auto-detect running services (nginx, postgres, redis, etc.)

**Step 3: Verify**

Go back to the platform. Your host should appear on the **Hosts** page within 1-2 minutes.

**Uninstall:**

```bash
curl -fsSL 'http://your-platform:8080/uninstall.sh?api_key=YOUR_KEY' | sudo bash
```

### Service Configuration

**URL:** `/service/:id/config`

After the agent discovers a service, you need to configure how to collect its data.

**For each discovered service, you can configure:**

| Setting | Description |
|---|---|
| **Log Collection** | Toggle on/off. Requires log file paths to be set. |

5. Click **Save**
6. Click **Generate Install Command** to get the integration script
7. Run the command on the host to start collecting data

### Integration Scripts

When you configure a service and click "Generate Install Command", the backend generates a bash script that:

1. Verifies it is running on the correct host (checks machine-id)
2. Backs up the existing otelcol config
3. Patches the config to add log receivers and metrics scrapers
4. Restarts the otelcol service
5. Reports status back to the platform

The script is pure bash — no Python required on the customer's server.

**Important:** The integration script must be run on the same host where the agent is installed. It modifies the agent's configuration to add service-specific collection.

### Alert Rules

**URL:** `/alerts` → Rules tab

Alert rules let you define conditions that trigger notifications when metrics or logs cross thresholds.

**60+ pre-built templates** covering:

| Category | Examples |
|---|---|
| Host | CPU > 90%, Memory > 85%, Disk > 90%, Swap > 50%, Load > 4 |
| Nginx/Apache | 5xx rate > 1%, P99 latency > 500ms, Connection saturation |
| PostgreSQL | Connections > 80%, Deadlocks detected, Cache hit < 95% |
| MariaDB | Similar to PostgreSQL |
| Redis | Memory > 80%, Evictions > 0, Cache hit < 90% |
| PHP-FPM | Worker saturation > 80%, Queue depth > 10, Slow requests > 5/sec |
| Container | Stopped, CPU > 90%, Memory > 90% |

**Creating an alert rule (3-step wizard):**

1. **Pick Service** — select the host and service type
2. **Pick Template** — choose from available templates for that service type
3. **Configure** — set threshold, severity (info/warning/critical), notification channels

**How the alert engine works:**

- A background goroutine evaluates all enabled rules on a configurable interval
- For each rule, it builds a PromQL or LogQL query from the template
- Queries VictoriaMetrics or Loki for the current value
- If the value crosses the threshold for the configured duration (default: 5 minutes), an alert event is created
- When the condition clears, the event is automatically resolved
- Email notifications are sent to configured channels on breach and resolution
- Related alert events are correlated into **incidents** with root cause analysis

**Managing rules:**
- Toggle rules on/off with the switch
- Edit rules (opens the wizard pre-filled)
- Delete rules (with confirmation)
- Acknowledge firing events

### Incidents

Incidents are automatically created when multiple related alert events fire on the same host or service. The platform correlates:

- **Cross-tier signals** — e.g., high CPU on a host + slow responses on nginx + connection spikes on postgres = one incident
- **Root cause analysis** — the incident identifies which service and tier (host/web/app/db/cache) is likely causing the problem
- **Confidence level** — high/medium/low based on signal correlation

View incidents on the **Overview** dashboard or dismiss them from the alert events page.

### CVE Vulnerabilities

**URL:** `/alerts` → Vulnerabilities tab

The platform automatically scans discovered services against the NIST NVD database:

1. The CVE scanner runs every 2 hours (configurable)
2. For each service with a known version, it queries NVD for matching CVEs
3. Results are filtered by severity (MEDIUM, HIGH, CRITICAL)
4. Findings appear in the Vulnerabilities tab with CVE ID, severity, CVSS score, and description

**Requirements:**
- Service version must be detected by the agent
- NVD API key is recommended (rate-limited without one)

## Removing pgAdmin for Production

pgAdmin is for development/database debugging only. To remove it:

1. Edit `docker-compose.yml`
2. Delete or comment out the `pgadmin` service:

```yaml
# pgadmin — dev only, remove for production
# pgadmin:
#   image: dpage/pgadmin4:latest
#   ...
```

3. Remove the `pgadmin-data` volume if desired:

```bash
docker volume rm platform_pgadmin-data
```

4. Restart:

```bash
docker compose up -d
```

## Troubleshooting

| Symptom | Fix |
|---|---|
| Frontend shows "Checking session..." forever | Backend is not running. Check `docker compose ps` and backend logs. |
| "Invalid email or password" on login | Check you are using the correct email. Passwords are case-sensitive. |
| Host not appearing after agent install | Wait 1-2 minutes. Check agent logs on the host. Verify API key is correct. |
| Services not discovered | The agent needs root access to scan for services. Run install script with `sudo`. |
| Logs not showing | Configure log paths on the service config page. Install the integration script on the host. |
| Metrics not showing | Configure the metrics endpoint on the service config page. Enable the exporter on the host. |
| Alert not firing | Check the rule is enabled. Verify the threshold and duration. Check the alert engine is running (backend logs). |
| AI report fails | Verify `GEMINI_API_KEY` or `GROQ_API_KEY` is set in the backend `.env`. |
| CVE data missing | Verify `NVD_API_KEY` is set. Without it, scanning is rate-limited. |
| "Account deactivated" page | Your admin deactivated your account. Contact your admin. |
| "Subscription expired" page | Select a new plan to reactivate, or contact your admin. |
| CORS errors | Update `CORS_ALLOW_ORIGINS` in backend `.env` to include your frontend URL. |
| Email not sending | Check SMTP credentials in backend `.env`. Emails are logged to console if SMTP is not configured. |
| Container not showing | Verify Docker socket is accessible to the agent. Check agent logs. |
